## 1. 背景

**2026年10月1日から、カスタマーハラスメント対策が全事業主の義務**となりました（改正労働施策総合推進法）。労働者を1人でも雇う事業主が対象で、企業規模・業種による適用除外はありません。

カスハラは「**顧客等**の言動であって、社会通念上許容される範囲を超えたものにより、労働者の就業環境が害されるもの」と定義されます。ここでいう顧客等には**取引の相手方も含まれる**ため、**B2Bの取引先からのハラスメントも対象**です。カスハラを「客が店員に怒鳴る」こととだけ捉えていると見落とす部分です。

事業主には、方針の明確化、**相談体制の整備**、事後の適切な対応、抑止のための措置が求められます（厚労省の防止指針は2026年2月告示、10項目）。ただし「社会通念上許容される範囲」に具体的な数値基準はなく、**どこからがカスハラかの線引きは各社に委ねられています**。

SaaS事業では、カスハラをしてくる相手が**契約者であり売上源**です。顧客との取引を見直すことは法的に取りうる措置ですが、それは解約と直結します。

## 2. このケースを立てた3つの観点

| # | 観点 | 中身 |
| --- | --- | --- |
| **①** | **新鮮さとタイムリーさ** | 施行直後で、企業として早急な対応が必要な状況そのものが**ビジネス現場感**を持つ。先行事例がないため、学生の提案が本当に新しくなりうる |
| **②** | **アイデアの広がり** | 相談窓口という「うまく機能していないしくみ」をAIで組み直す題材。さらに**顧客＝売上源というトレードオフ**があり、作るものが収束しにくい |
| **③** | **協賛企業へのインパクト** | 対象が労働者を1人でも雇う全事業主。協賛企業も審査員も自社で対応しなければならない立場にあり、他人事にならない |

### 補強として効く点

- **複数の課題意識が同居している。** 惣菜工場は「不良の原因はどこか」、農業法人は「転記と提出の手間」と、題材が一つの課題に収まる。このケースには、従業員の保護・顧客対応の質・製品の分かりにくさ・営業とCSの期待値のずれ・離職・解約が同居しており、**どこに着目するかから競える**
- **線引きそのものを設計することが提案になる。** カスハラは「社会通念上許容される範囲」としか定義されておらず、どこからがカスハラかは各社に委ねられている。方向性で競う設計と最も噛み合う
- **学生の志望業界と重なる。** 惣菜工場の代表やスーパーの店長になる学生はほぼいないが、SaaS・IT企業は主要な進路。カスタマーサクセス、チャーン、SLAといった語彙がそのまま出てくる
- **トレードオフが本物。** 「問題顧客を切る」で離職は減るが解約が増える。ビジネスコンテストで議論されるべき判断そのもの
- **データ量が3案中最多。** プロダクト利用ログを含めて約100万行。データサイエンスを学ぶ学生にも向き合う対象がある

## 3. 舞台

| 項目 | 設定 |
| --- | --- |
| 会社 | 中小企業向けの業務SaaS（勤怠・経費管理）を提供（社名は架空） |
| 従業員 | 180名（開発60、営業45、CS35、コーポレート40） |
| 顧客 | 契約1,200社。年間経常収益（ARR）約22億円 |
| サポート体制 | メール・チャット（平日9〜18時）、電話は折り返し。上位プランの120社には専任CSとSlack共有チャネル |
| CS部門 | 35名。離職率は年28%（全社は12%）※**ケース文には書かない**。データから読み取れる値として置く |
| 対応状況 | 2026年春に相談窓口・方針・エスカレーションルールを整備。10月の施行時点で指針の措置は形式上満たしている |

## 4. 登場する人（運営用の設定）

課題発見型のケースなので、**配布するケース文では「誰が何に困っているか」を断定しません。** 以下は運営が持っておく設定で、データの中に痕跡として現れるもの。

| 人物 | 置かれている状況（データに現れる形） |
| --- | --- |
| **CS本部長（38歳）** | 措置は満たしたが、機能しているかを示すものがない。経営会議で報告を求められている。視点人物 |
| CSメンバー（35名） | 「お客様だから」と抱える。相談窓口があることは知っているが使わない。→ 社内メモ、稼働ログの時間外、意識調査の自由記述に現れる |
| 営業部門 | 解約されたくないので顧客に強く出られない。→ 契約記録、Slackの発言、提案資料のサポート範囲ページに現れる |
| CFO | CSの採用と教育コストが膨らんでいる。離職1名あたり約180万円 | → 離職記録、勤怠、稼働ログに現れる |

## 5. すでに解決を試みたこと

ケース文に含める前提。これがないと「まず相談窓口を作れば」「AIチャットボットを入れれば」という提案が出てしまう。

- **2026年春に相談窓口を設置した。** 方針文書を作り、エスカレーションルールも定めた。全メンバーに周知した
- **一次対応にAIチャットボットを導入した。** 簡単な問い合わせは減ったが、**難しい顧客だけが人に回る形になり、むしろ濃縮された**
- **SLAを整備した**（初回返信4時間以内）。守れているが、守るために無理をしている場面がある
- **エスカレーションルールを作った。** 「暴言・長時間拘束があれば上長へ」と書いてあるが、何が暴言かの判断がメンバーに委ねられている

→ 制度もツールも入れた。それでも**実態はチケットとSlackの中にあり、相談窓口とつながっていない**。

## 6. 配布用ケース文

**このケースは課題発見型です。** 解くべき課題と成功の形は、こちらで決めません。参加者がデータから見つけて定義します。

> あなたは、中小企業向けの業務SaaSを提供する従業員180名の会社で、カスタマーサクセスを統括しています。契約は1,200社、CS部門は35名です。
>
> 今年の春、カスハラ対策の義務化を見据えて、相談窓口を設け、方針を掲示し、エスカレーションルールを定めました。一次対応にはAIチャットボットも入れました。10月に法律が施行され、設置から半年あまりが経ちます。
>
> **措置は満たしています。** 窓口はあり、方針はあり、ルールもある。監督署から指摘を受ける状態ではありません。
>
> 窓口に上がってきた相談は、14件です。
>
> その数が多いのか少ないのか、あなたには判断がつきません。カスハラが起きていないならそれでいい。起きているのに上がってきていないなら、窓口は機能していないことになります。どちらなのかを示すものを、あなたは持っていません。
>
> 手元にあるのは、2年分の記録です。サポートチケットが約8万件（本文と社内メモ込み）、顧客との共有Slackチャネルが約3.5万件、プロダクトの利用ログが約88万行。契約・更新・解約の記録、CSメンバーの稼働ログと勤怠、在職者の意識調査と退職面談の記録、顧客満足度の回答、電話と会議の録音、顧客から届いたエラー画面のスクリーンショット。どれも、何かのために取られて、そのまま置かれています。
>
> 来月の経営会議で、窓口を設けてからの半年について報告することになっています。
>
> **さて、このデータを見て、何が問題だと考えますか。そしてAIを使って何をしますか？**
>
> ---
>
> **提出するもの**
>
> | # | 内容 |
> | --- | --- |
> | 1 | **あなたが設定した課題。** データの何を根拠にそう考えたか |
> | 2 | **あなたが定義した成功の形。** 何がどうなれば成功なのか、どう測るのか |
> | 3 | **そこへ向かうアプローチ**と、動くもの |
>
> *方向性：守るのは働く人です。従業員を監視したり、担当者の評価に使う道具にはしないでください。顧客との取引を見直すことは選択肢に入りますが、「この顧客は危険」と機械が一方的に決める形は求めていません。判断は人が行います。*
>
> *なお、この制度は2つの失敗を同時に禁じています。労働者を守らないことと、**正当な苦情をカスハラと決めつけて抑圧すること**です。どちらにも倒れない線の引き方を考えてください。*

### なぜ課題を示さないのか

ケース文には「離職率が高い」「解約が怖い」といった課題意識を**書きません**。書けば、それが唯一の課題になります。

実際の施行直後の企業は、まさに「措置は満たしたが、何が起きているか分からない」状態にいます。**その状態をそのまま渡すのが、最も正直で、最も広がりのあるケースになります。**

データの中には、離職記録も在職者意識調査も解約記録も製品の利用ログも入っています。離職に着目したいチームはそこへ行けますし、製品の分かりにくさに着目したいチームもそこへ行けます。**どこに着目するかの判断が、最初の勝負になります。**

### 審査の順序（このケースの場合）

| 順位 | 見るもの |
| --- | --- |
| **1** | **どんな課題と成功の形を立てたか。** データの何を根拠にそう決めたか |
| 2 | アプローチの筋。その課題に対して、なぜその方向を選んだか |
| 3 | 効き方の理屈。自分で立てた成功の形に、その方向が効く筋道があるか |
| 4 | 実装の完成度 |

チームごとに成功の形が違っても、**「自分で引いたハードルの高さと、それを越えた度合い」**を見るので審査は成立します。低いハードルを選んだチームは1で負けます。

## 7. 運営メモ：想定される方向（参加者には示さない）

課題そのものを参加者が決めるため、ここに挙げるのは**「こういう課題を立てて、こう攻めることがありうる」**という見込み。ここにない課題を立てたチームは、減点ではなく加点。

| # | 方向 | 何を作るか | 成功の形への効き方 |
| --- | --- | --- | --- |
| 1 | 実態を経営に届ける | チケットの社内メモとSlackから、負荷の実像を月次で集約する | 14件しか見えていない状態を変える |
| 2 | 線引きを現場に返す | 過去の事例から「これは相談していい」基準をCSの言葉で作る | 相談のハードルが下がる |
| 3 | 報告の摩擦を下げる | チケットを閉じる操作がそのまま相談になる | 二重に書かせない |
| 4 | 顧客ごとの向き合い方を設計する | 負荷と収益を並べ、プラン変更・契約条件の見直し・担当体制の変更を提案する | **解約を増やさずに負荷を下げる** |
| 5 | 発生の構造を突く | 製品の不具合・仕様の分かりにくさ・ヘルプの不足と発生の関係を示す | 原因を製品側で断つ |
| 6 | その場を支える | 対応中のCSに次の手と文面の候補を示す | 長時間化を防ぐ |
| 7 | 負荷を分散する | 担当顧客の組み替え、時間外の受け方を変える | 特定の担当に集中する構造を崩す |
| 8 | 相談の「その後」を返す | 何がどう対応されたかを本人に届ける | 報告した意味を実感できる |
| 9 | 離職の手前を捉える | 稼働ログ・意識調査から、辞める前に現れる変化を扱う | 成功の形に直接効く |
| 10 | 営業とCSの間を埋める | 契約時の期待値と実際のサポート範囲のずれを示す | 無理な要求の源を断つ |

### データの配置図

```
相談窓口（14件）        ← 制度上の正式な経路。ほぼ機能していない
   ▲
   │ 上がってくるのは深刻なものだけ
   │
社内メモ（1.2万件）      ← CSが書き残す。誰も読み返さない
   ▲
   │ 書かれるのは一部
   │
顧客とのやりとり
   ├─ Slack共有チャネル（3.5万件）   深夜・休日の書き込みが残る
   ├─ チケット本文（24万行）          やりとりそのもの
   ├─ 通話記録（800件）              電話と会議
   ├─ スクショ（600枚）              顧客が送ってくる画面
   └─ 利用ログ・契約・稼働（約95万行） 状況の数値的な痕跡
```

課題は**この三角形の下から上への流れが細い**ことにある。相談窓口だけを見ても何も分からない設計にしてある。

## 9. 意図的に仕込む「使い方の難」

| 種類 | 具体 |
| --- | --- |
| 書き手の癖 | 社内メモの書き方がCS35名で違う。詳細に書く人、「対応済」で済ませる人、絵文字で感情を示す人 |
| 記述の欠落 | 繁忙期（月初・月末の締め処理期）は社内メモが減る。書く時間がないため |
| 表記ゆれ | 「クレーム／苦情／ご指摘／お申し出／強い要望」が混在。深刻度と語彙が対応していない |
| 顧客IDの不整合 | 社名変更・分社化で同一顧客に別IDが振られているものが約15社分 |
| 時刻の粒度と時差 | チケットは秒単位、Slackはミリ秒、利用ログは日次。一部の顧客は海外拠点でUTC記録 |
| 退職理由の形骸化 | 届出上の理由は「キャリアチェンジ」が約7割。選択肢に「業務負荷」はあるが使われていない |
| 匿名の壁 | 在職者意識調査は個人に紐づかない。部門・等級・勤続区分までしか辿れない |
| エスカレーションの不記録 | ルール上の条件に該当するのに、エスカレーションのフラグが立っていないチケットがある |
| 文字起こしの誤り | 固有名詞の誤変換が混在。話者分離も一部失敗している |
| スクショの雑多さ | 画面全体・一部切り抜き・スマホでの画面撮影が混在。文字が読めないものも含む |
| 手書き | 退職面談のメモは筆跡がばらばらで、日付の記載がないものがある |

## 10. 仕込んだ現象（運営用・非公開）

**「正解」とは呼ばない。** 課題発見型のケースなので、ここに挙げるのは**課題の種**であり、「このデータからは少なくとも9通りの課題が立てられる」ことの保証である。

**見つけた数で採点してはいけない。** それをやると当てっこに戻る。**私たちが仕込んでいない課題を立てたチームは、減点ではなく加点**とする。

| # | 仕込む事実 | 発見の経路 | 段 |
| --- | --- | --- | --- |
| A | SLAを超過したチケットの顧客は、再オープン回数が平均2.8倍 | チケットのメタデータ | 1 |
| B | **特定の20社がチケット総数の18%を占めるが、そのうち12社はプラン単価が中位**。売上貢献と負荷が比例していない | チケット × 契約 × 顧客マスタ | 1 |
| C | 離職したCS担当は、「負荷上位20社」の担当比率が平均の2.1倍だった | 稼働ログ × 顧客マスタ × 離職記録 | 1 |
| D | 社内メモに「苦慮」「過大」等の記述があるチケットは、クローズまでの日数が3.2倍 | 社内メモの分類 × チケット | 2 |
| E | 在職者意識調査の「顧客対応の負担感」が高い回次の半年後に、離職が増えている | 意識調査 × 離職記録（回次単位） | 2 |
| F | 解約140社のうち、カスハラ的な連絡が多かった顧客の解約率は、全体平均と**変わらない**（＝強く出ても失わない可能性を示す） | 解約記録 × チケット × Slack | 2 |
| G | Slackの深夜・休日の書き込みは、特定の8社に集中している | Slack共有チャネルの時刻分析 | 3 |
| H | エスカレーションルールの条件に該当していたのに、エスカレーションされなかったチケットが約2割 | エスカレーションルール（文書）× チケット | 3 |
| I | エラー画面のスクショのうち一定数は、製品の不具合ではなく顧客側の操作に起因している | スクショ × チケット本文 | 4 |

A〜C が1段目で到達可能、D〜F が2段目、G・H が3段目、I が4段目。**1段目だけで3つ、2段目までで6つ**見つかる配分にしている。

**Fが最も価値のある現象。** 「負荷の高い顧客に毅然と対応しても、解約率は上がらないかもしれない」という示唆は、成功の形の2条件を両立させる筋そのものになる。

## 11. 弱点と、対処の見込み

| 弱点 | **データ側での対処** |
| --- | --- |
| **学生にCS業務の経験がない** | ケース文にSlackの実際の文面（深夜1時の「まだ直らないんですか」など）を入れて、具体で想像させる。配布データにも生の文面が大量にある |
| **B2Bのカスハラが典型イメージから外れる** | 背景で「顧客等には取引の相手方も含まれる」ことを明記する。これは盲点であり、同時に新鮮さの源でもある |
| 効果測定が難しい（離職の真因が追えない） | **解約記録140社と在職者意識調査（匿名・年2回・4回分）を入れる。** 個人の因果は追えないが、回次単位・部門単位で比較できる。現象E・Fがその経路になる |
| データ量が多く初動が重い | 全ファイルを読み込むサンプルコードを同梱し、1段目だけで到達できる現象（A〜C）を用意する |
| **課題発見型のため、1日目で止まるチームが出る** | 事前プログラムでサンプルデータ（全体の約1割）を配り、構造を掴んだ状態で当日に入らせる。Day1午後の中間フィードバックで「どんな課題を立てたか」を全チームに言わせ、立てられていないチームをその場で引き上げる |
| **課題が制度から外れる方向へ流れる** | たとえば「チケット対応を速くする」はサポート改善であってカスハラ対策ではない。方向性の但し書きで「守るのは働く人」と明示し、中間フィードバックで軌道を戻す |
| センシティブさ | 事例の強度を**3段階**に分け、重度は1割に絞る（軽度7割・中度2割）。**暴力・性的な内容は含めない。** 配布物の冒頭に扱いの注意書きを置く |
| 合成データが作りにくい | 骨格（**場面 × 言動 × 継続時間 × 対応 × 結果**）の組み合わせで生成し、口語の揺れとCS35名の書き癖を後から注入する。場面はチャット・メール・電話・Slack・オンライン会議の5種、言動は深夜連絡・人格否定・無償対応の強要・過大な要求・担当者の変更要求の5種を基本形とする |
