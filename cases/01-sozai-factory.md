## 1. 背景

**HACCP**（危害要因分析・重要管理点）は、食品の製造工程のうち危険が起こりうる箇所を特定し、そこを継続的に監視・記録する衛生管理の手法です。日本では**2021年6月から、原則すべての食品事業者に義務化**されました。小規模事業者も対象で、簡略化された手引書に沿った運用が認められています。

惣菜製造では、原材料の受入温度、加熱の中心温度（一般に**75℃で1分以上**）、冷却時間が重要管理点にあたり、毎回の記録が必須です。加えて清掃記録と従業員の健康チェックも日々残します。

取引先のスーパーは年2回ほど工場を訪れて監査を行い、記録の提示を求めます。**指摘が続けば取引停止につながる**ため、中小の食品工場にとって記録は「取引を維持するためのもの」になりやすい構造があります。

## 4. すでに解決を試みたこと

ケース文に含める前提です。これがないと「まずBIツールを入れれば」という提案が出てしまいます。

- **3年前：手書きからHACCP記録アプリへ移行**。監査対応は楽になり、PDFで過去分を提示できるようになった
- **アプリには閾値超過のアラート機能がある**。月に1〜2回鳴るが「入力ミス」として訂正されることが多く、現場は信用していない
- **BIツールの導入を検討**したが、グラフを作っても「見て何をすればいいのか」が分からず、見積段階で止まった
- **クレームのたびに原因を探る**が、該当日の記録に異常値はなく「原因不明」で終わる

→ 記録は構造化されて溜まっているのに、**どの記録とどの結果が結びついているかを誰も追えていない**。

## 5. 配布用ケース文

> あなたは、スーパー向けの惣菜を作る従業員12名の工場の代表です。
>
> クレームは年に40件。3年前にHACCP記録アプリを導入し、原材料の受入温度、加熱の中心温度、冷却時間、清掃、従業員の健康チェックを毎日タブレットで記録するようにしました。取引先の監査ではPDFを提示すれば済むようになり、指摘も減りました。それでもクレームの件数は、導入前と変わっていません。
>
> クレームが出るたび、あなたは該当日の記録を見返します。しかし閾値を外れた数値は見つからず、毎回「原因不明」で終わります。取引先には「以後気をつけます」と伝えるしかありません。次の監査は2か月後です。
>
> 記録係を兼ねる製造リーダーは「入力する時間はあっても、見返す時間はない」と言います。手元には2年分の記録が約39万行。クレーム記録、社内の不適合記録、微生物検査結果、監査指摘、受入時とクレーム時の写真、アプリ導入前の手書き記録も残っています。
>
> **さて、AIを使って何をしますか？**
>
> **成功の形：クレームを年40件から減らす。ただし記録にかける時間は増やさない。**
>
> *方向性：記録を減らすことが目的ではありません。判断は人が行います。*

2つ目の条件（記録時間を増やさない）で、「もっと細かく記録すれば分かる」という安易な方向を封じています。現場の手を止めず、すでにある記録で何とかするという制約が判断を生みます。

## 6. 運営メモ：想定される方向（参加者には示さない）

| 方向 | 中身 |
| --- | --- |
| 原料・仕入先から攻める | 受入時の判断基準や仕入先との取り決めを変える |
| 工程から攻める | 繁忙日の冷却・工程設計を見直す |
| 記録の質から攻める | 中心温度が75.0に集中する現象そのものを扱う（測り方・書き方を変える） |
| クレーム側から攻める | 申立内容から該当製造日・ロットを絞る精度を上げ、原因追跡を成立させる |
| 設備から攻める | 冷蔵設備の状態変化を扱う |
| 返し方から攻める | 製造リーダーが朝礼で使える形にする |

## 8. 意図的に仕込む「使い方の難」

| 種類 | 具体 |
| --- | --- |
| 表記ゆれ | 製品名「ポテトサラダ／ポテサラ／Pサラダ」、担当者「佐藤／佐藤M／さとう」 |
| 単位混在 | 数量の kg / g / ケース / 本、温度の「8.2」「8.2℃」「8度」 |
| 欠損 | 受入温度の欠損 約7%、ロットNo欠損 約12%、繁忙日の清掃記録の未入力 |
| 時刻のずれ | 冷蔵庫ログはUTC、アプリ記録はJST。操作ログの端末TB-02は時刻が約3分進んでいる |
| 前工程との断絶 | 加熱記録の「使用原料ロット」が、受入記録のロットNo表記と一致しないものが 約20% |
| 丸め癖 | 中心温度が基準75℃に対し「75.0」「75.1」に不自然に集中（実測より記入習慣の反映） |
| 値の書き換え | 操作ログには修正前の値が残るが、台帳CSVには最終値しかない。両者を突き合わせないと訂正の実態が見えない |
| 自由記述 | 製造日報の特記事項、クレーム申立内容、不適合の内容が口語・略語まじり |
| 写真の紐付け | 受入写真200枚のうち約15%はファイル名がレコードと対応しない（撮ったが記録に貼らなかった） |
| 旧形式 | アプリ導入前6か月分が手書きPDFスキャン。書き手3名で癖が違う |

## 9. 仕込んだ現象（運営用・非公開）

**「正解」とは呼ばない。** 役割は「このデータは解ける」ことを運営が保証するための自己検証のみ。採点表には載せない。

| # | 仕込む事実 | 発見の経路 | 段 |
| --- | --- | --- | --- |
| A | 特定仕入先の鶏肉ロットで、7〜9月の受入温度が基準上限付近に偏る。該当ロットを使った製品にクレームと不適合が集中 | 受入記録 × 加熱記録の原料ロット × クレームの推定製造日 | 1 |
| B | 製造数が上位10%の日に、冷却の所要時間が平均より30%長い。翌週の微生物検査値も高い傾向 | 製造日報 × 冷却記録 × 微生物検査 | 1 |
| C | 金曜午後の週次清掃が、月末の繁忙日に未入力になりやすい。その翌週に不適合が出る確率が上がる | 清掃記録の欠損パターン × 不適合記録 | 1 |
| D | 冷蔵庫1台が、2年目の秋以降に設定温度へ復帰する時間が延びている（劣化の兆候） | 温度自動ログの時系列 | 1 |
| E | 閾値アラートの約7割が「訂正」で閉じられ、その訂正が特定の担当者と早朝の時間帯に偏る | 操作ログ × 加熱記録 | 2 |
| F | 手書き期間の受入温度は、アプリ期間より分散が大きい（アプリ導入後に記録が均質化＝丸められている） | 手書きPDF × 受入記録 | 3 |
| G | 外観判定が「良」なのに、写真では変色が見えるものが数件ある。うち2件はのちにクレームへ | 受入写真 × 受入記録 × クレーム | 4 |

A〜Dが1段目で到達可能、E が2段目、F・G が3・4段目。**1段目だけで4つ見つかる設計**にしている。

## 10. 弱点と、対処の見込み

| 弱点 | 対処 |
| --- | --- |
| **業界が学生に遠い** | ケース文の語り口（二人称・数字先出し）では改善したが、**業界そのものは変えられない** |
| **検出の精度競争に引っぱられる** | 「中心温度75℃で1分以上」という法令基準があるため、基準違反を見つける競争に寄りやすい。成功の形を「クレームを減らす」に置いて緩和しているが、構造的な引力は残る |
| クレーム80件では統計的に薄い | 社内の不適合記録400件を足して、1段目で扱える件数を確保した |
