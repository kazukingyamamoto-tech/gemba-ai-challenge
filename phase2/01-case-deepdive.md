## 1. ケース設計の考え方

これまでの検討で定まった、GEMBA AI Challenge のケースを作るうえでの理想形。

### 1-1　型：「問題の具体的提示 → では、AIでどうする？」

国内外のAIハッカソンを調査した結果、参加者の成果物が実務に近づいたケースはすべて、**具体的な困りごとから始まり、解法は参加者に委ねる**形をとっていました。逆に「この技術で何ができる？」から始める技術シーズ型は、GEMBAが目指す「現場」から遠くなります。

ケースは次の一文に収まる形で書きます。

> **「〇〇の現場で、△△な人が、□□のせいで困っている。（あるデータ・素材はこれ）。AIで何ができる？」**

### 1-2　描くのは「記録はあるのに、報われていない」状態

「データがない」課題は、結局センサーを付ける・アプリを入れるという話になり、AIの出番が小さくなります。扱うべきは**データはあるのに活かせていない現場**です。

現場はすでにデジタル化されている前提で書きます。CRM・会計SaaS・記録アプリ・チャットは入っている。それでも残る問題を描く。責めるのは人ではなく、**記録の形式やツールが、実際に起きていることに合っていないこと**です。

「なぜこれまでのSaaSで解決しなかったのか」に答えられることも条件になります。答えは、現場で起きていることの大半が非構造（会話・写真・チャット・手書き）で、構造化された入力欄を良くしても解決しないから。ここに「AIで何ができる？」と聞く必然性があります。

### 1-3　制度は背景に置き、主題にはしない

3-1のHACCP、3-3のJGAPのように、**近年の法改正で記録が義務づけられた**制度を背景に使うと、「なぜこの記録が存在するのか」を説明せずに済み、「まだ誰も活かせていない」ことが事実として言えます。

ただし制度名をケースの主題にすると、参加者が法令解釈に時間を取られ、AIの検討に入る前に止まります。**制度は背景の1〜2文に留め、課題本体は記録の活用に置く**という距離感を守ります。

### 1-4　成功の形は「方向性で競える」ように書く

競ってほしいのは、**同じゴールに対して違う筋道を持ち寄ること**です。性能はその次に来ます。この順序は成功の形の書き方だけで決まります。

| # | 基準 | 悪い例 | 良い例 |
| --- | --- | --- | --- |
| 1 | **手段を表す語を含まない** | 予測する／要約する／検出する／分類する／検索できる | 減る／増える／早くなる／止まらない |
| 2 | **現場の誰かの行動か、経営の数字が変わる形** | 「傾向が可視化される」 | 「職長が午後の段取りを変える」「クレームが減る」 |
| 3 | **異なる方向のアプローチが3つ以上思いつく** | 到達経路が1つ＝手段を書いてしまっている | — |
| 4 | **測り方が言える** | 「現場が助かる」 | 「月○時間」「年○件」 |

**3が最も重要な検査**です。ケース文を書いたら、運営側で「この成功の形に、方向の違う解き方を3つ挙げられるか」を必ず試します。

また、**成功の形は2条件にする**と効きます。片方だけなら安易に達成できてしまう場合、2つ目の条件がトレードオフとして効き、どこで折り合いをつけるかがアプローチの差になります。

### 1-5　審査の優先順位

| 順位 | 見るもの |
| --- | --- |
| 1 | **アプローチの筋**：なぜその方向を選んだか。現場の誰が、いつ、どう使うのか |
| 2 | **成功の形への効き方**：その方向で数字が動く理屈が立っているか |
| 3 | **性能・完成度**：実際に動くか、精度はどうか |

性能を3番目に置くことを、募集要項と当日の説明で明示します。そうしないと参加者は精度を上げに行きます。

### 1-6　この2ケースを選んだ理由

| 観点 | 3-1 惣菜工場 | 3-3 農業法人 |
| --- | --- | --- |
| 難の性質 | **溜めた記録を誰も読み返さない**（出力先は監査だけ） | **同じ記録を4つの様式に書き直している**（変換が人力） |
| 問われる力 | 蓄積データから傾向・異常・因果の候補を見つける（**読む側**） | 非構造の入力を構造化し、複数の出力様式へ変換する（**書く側**） |
| 現場感 | 製造ラインの合間のタブレット入力、油と水のある環境、パートの入れ替わり | 畑からのLINE報告、夜に台所で入力、天候に左右される作業 |
| ビジネス感 | 取引先監査、クレーム対応コスト、品質事故による取引停止リスク | 出荷先3社との取引継続条件、JGAP認証の維持、補助金 |

2ケースで「読む側」と「書く側」の両方を扱えるため、参加者の成果物が同じ方向に集まりません。また両ケースとも、記録の様式が法令・認証で定まっているため、実データを使わなくても現実に近いダミーデータを設計できます。

## 2. ケース3-1　惣菜工場

### 舞台

| 項目 | 設定 |
| --- | --- |
| 会社 | 惣菜製造（社名は架空。配布時に決定） |
| 所在 | 地方都市の郊外、工業団地内の自社工場1棟 |
| 従業員 | 12名（代表1、製造リーダー1、製造パート8、配送2） |
| 製品 | 惣菜20品目（煮物、和え物、サラダ、揚げ物、炒め物） |
| 取引先 | 地域スーパー3社（計18店舗）、直売所2か所 |
| 売上 | 年商約2億円 |
| 認証 | HACCPに沿った衛生管理。取引先による年2回の工場監査あり |

### 困っている人

| 人物 | 困っていること |
| --- | --- |
| 製造リーダー・佐藤（45歳） | 記録係を兼任。入力する時間はあるが、見返す時間がない |
| 代表（61歳） | 監査は通るが、クレームが減らない。原因が分からないまま謝っている |
| 製造パート（8名、勤続1か月〜15年） | アプリの入力項目の意味が分からないまま、前回と同じ数字を入れることがある |

記録は1日を通して発生します（受入・健康チェック・加熱・冷却・製造日報・清掃・自動温度ログ）。内訳は [`02-data-design.md`](02-data-design.md) を参照。

### すでに解決を試みたこと

ケース文に含める前提です。これがないと「まずBIツールを入れれば」という提案が出てしまいます。

- **3年前：手書きからHACCP記録アプリへ移行**。監査対応は楽になり、PDFで過去分を提示できるようになった
- **アプリには閾値超過のアラート機能がある**。月に1〜2回鳴るが「入力ミス」として訂正されることが多く、現場は信用していない
- **BIツールの導入を検討**したが、グラフを作っても「見て何をすればいいのか」が分からず、見積段階で止まった
- **クレームのたびに原因を探る**が、該当日の記録に異常値はなく「原因不明」で終わる

→ 記録は構造化されて溜まっているのに、**どの記録とどの結果が結びついているかを誰も追えていない**。

### 配布用ケース文

> スーパー向けの惣菜を作る、従業員12名の工場。3年前にHACCP記録アプリを導入し、原材料の受入温度、加熱の中心温度、冷却時間、清掃、従業員の健康チェックを、毎日タブレットで記録している。取引先の監査ではPDFを提示すれば済むようになり、指摘も減った。
>
> それでも、クレームは年に40件前後で変わらない。クレームが出るたび該当日の記録を見返すが、閾値を外れた数値は見つからず「原因不明」で終わる。記録係の製造リーダーは「入力する時間はあっても、見返す時間はない」と言い、代表は「2年分の記録が溜まっているのに、そこから何も分かっていない」と言う。
>
> 2年分の記録（約39万行）と、同期間のクレーム記録・社内の不適合記録・微生物検査結果・監査指摘、受入時とクレーム時の写真、アプリ導入前の手書き記録がある。**AIで何ができる？**
>
> **成功の形：クレームを年40件から減らす。ただし記録にかける時間は増やさない。**
>
> *方向性：記録を減らすことが目的ではありません。判断は人が行います。*

2つ目の条件（記録時間を増やさない）で、「もっと細かく記録すれば分かる」という安易な方向を封じています。現場の手を止めず、すでにある記録で何とかするという制約が判断を生みます。

### 運営メモ：想定される方向（参加者には示さない）

| 方向 | 中身 |
| --- | --- |
| 原料・仕入先から攻める | 受入時の判断基準や仕入先との取り決めを変える |
| 工程から攻める | 繁忙日の冷却・工程設計を見直す |
| 記録の質から攻める | 中心温度が75.0に集中する現象そのものを扱う（測り方・書き方を変える） |
| クレーム側から攻める | 申立内容から該当製造日・ロットを絞る精度を上げ、原因追跡を成立させる |
| 設備から攻める | 冷蔵設備の状態変化を扱う |
| 返し方から攻める | 製造リーダーが朝礼で使える形にする |

## 3. ケース3-3　農業法人

### 舞台

| 項目 | 設定 |
| --- | --- |
| 法人 | 農業法人（社名は架空） |
| 所在 | 地方の平坦地。圃場は自宅から半径3km内に点在 |
| 従業員 | 9名（代表、代表の妻、息子、常勤3、パート3） |
| 圃場 | 12圃場（露地8・ハウス4）、計3.2ha |
| 作物 | トマト、きゅうり、ほうれん草、小松菜、ブロッコリー |
| 出荷先 | スーパー3社、JA、直売所2、EC（少量） |
| 売上 | 年商約6,000万円 |
| 認証 | JGAP（取得3年目）。年1回の審査あり |

### 困っている人

| 人物 | 困っていること |
| --- | --- |
| 代表の妻（52歳） | 事務・記録の一元担当。夜にLINEを見ながらアプリへ転記し、提出のたびに様式ごとに書き直す |
| 代表（58歳） | 「同じことを4回書いている。記録のせいで畑に出る時間が減っている」 |
| 常勤・パート（6名） | 報告の書き方は各自流。「A圃場」「Aハウス」「上の畑」が同じ場所を指す |

### 記録が4回書き直される経路

```
畑（作業者6名）
  │ LINEグループに報告（テキスト＋写真、1日5〜15件）
  ▼
代表の妻（夜、台所）
  │ 目で読んで転記
  ▼
営農管理アプリ（JGAP対応・作業/農薬/肥料/収穫/出荷）
  │
  ├─→ ① JGAP審査用の記録（アプリから出力できる：唯一楽な経路）
  ├─→ ② スーパーA社「栽培履歴書」Excel：品目ごとに別シート、農薬は商品名、月単位
  ├─→ ③ スーパーB社「生産履歴」Excel：農薬は有効成分名で記載、収穫ロット単位
  ├─→ ④ スーパーC社：Web入力用CSV、農薬コード必須（同社のコード表に従う）
  └─→ ⑤ 補助金実績報告（行政様式）：作付面積・労働時間・販売金額、四半期単位
```

②〜⑤は、元が同じ作業記録なのに、**項目名・単位・集計期間・農薬の呼び方がすべて違う**ため、アプリの出力を見ながら手で作り直しています。

### すでに解決を試みたこと

- **2年前に営農管理アプリを導入**。JGAPの記録はこれで出せるようになった
- **CSV出力からExcelマクロを作ろうとした**が、出荷先の様式が毎年少し変わり、1年で使えなくなってやめた
- **作業者にアプリを直接入力させようとした**が、畑で手袋をしたまま項目を選ぶのが現実的でなく、LINE報告に戻った
- **農薬の商品名と有効成分名の対応表を自作した**が、新しい農薬を使うたびに更新が必要で、半年で放置された

→ 記録の入口（LINE）と出口（4つの様式）のあいだの変換が人力のまま残っている。

### 配布用ケース文

> 野菜を作る従業員9名の農業法人。作業者は畑からLINEグループに「A圃場 トマト 摘芯 3名 9:00-11:30」と写真付きで報告し、事務担当（代表の妻）が夜にそれを読んで営農管理アプリへ入力する。JGAPの記録はアプリから出せるようになった。
>
> しかし出荷先のスーパー3社は、それぞれ別のExcel様式で栽培履歴の提出を求める。A社は農薬を商品名で、B社は有効成分名で、C社は自社の農薬コードで書くよう指定してくる。集計単位も月・収穫ロット・作付とばらばらだ。補助金の実績報告は行政の様式で、労働時間の集計を求められる。どれも元は同じ作業記録なのに、様式ごとに手で書き直しており、記録と提出にかける時間は月に25時間を超える。去年は提出物の誤記で1件差し戻され、出荷先から改善を求められた。
>
> 代表は「同じことを4回書いている。記録のせいで畑に出る時間が減っている」と言う。
>
> 2年分のLINEログ（約7,000件・写真とボイスメッセージ付き）、営農管理アプリのデータと操作ログ、出荷先3社の様式と過去の提出物、差し戻しの履歴、補助金の実績報告、アプリ導入前の手書き日誌がある。**AIで何ができる？**
>
> **成功の形：記録と提出にかかる時間（現状 月約25時間）を半分にし、提出物の差し戻しをゼロにする。**
>
> *方向性：提出をなくすことはできません。提出前の最終確認は人が行います。*

これも2条件です。時間だけなら「雑に作る」で達成でき、差し戻しゼロだけなら「今より丁寧に時間をかける」で達成できてしまいます。両立させる必要があることが判断を生みます。

### 運営メモ：想定される方向

| 方向 | 中身 |
| --- | --- |
| 変換を機械に寄せる | 様式間のマッピングを作る（最も素直な方向） |
| 入力を変える | LINEの書き方に型を与える。写真の使い方を変える |
| 確認だけを機械に任せる | 作るのは人、提出前チェックを機械が行う |
| **様式の側に手を入れる** | 出荷先3社に共通フォーマットを提案する材料を作る。技術の精度ではなく交渉で勝負する筋 |
| 記録の意味を変える | 栽培改善や販売に使えるようにして、記録のコストを別で回収する |
| 二重入力をなくす | LINEとアプリの転記そのものを経路から外す |
