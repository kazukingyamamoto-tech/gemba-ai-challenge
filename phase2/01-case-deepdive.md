## 1. この2ケースを採用した理由

### 1-1　「データを集められてはいるが、使い方に難がある」状況を扱いたい

GEMBA AI Challenge で参加者に向き合ってほしいのは、**データがない現場ではなく、データはあるのに活かせていない現場**です。

「データがない」課題は、結局センサーを付ける・アプリを入れるという話になり、AIの出番が小さくなります。一方「データはあるが使えていない」課題は、次の3つが同時に問われるため、AIを使う必然性が生まれます。

- 溜まっている記録の大半が**非構造**（自由記述・写真・チャット・手書きスキャン）である
- 記録の**形式が目的に合っていない**（監査に出すために作られ、改善には使えない）
- 記録が**複数の場所に分かれている**（システムごと、提出先ごとに別の形で存在する）

この観点で9本のケースを見直すと、3-1と3-3は「記録はすでに毎日取られており、量もある。しかし誰もそこから何も引き出せていない」という状況が最も明確でした。

| | 3-1 惣菜工場 | 3-3 農業法人 |
| --- | --- | --- |
| 記録は取れているか | 取れている（HACCP記録アプリ、2年分） | 取れている（LINE＋営農管理アプリ、2年分） |
| 難の性質 | **溜めた記録を誰も読み返さない**（出力先は監査だけ） | **同じ記録を4つの様式に書き直している**（変換が人力） |
| 参加者に問われる力 | 蓄積データから傾向・異常・因果の候補を見つける | 非構造の入力を構造化し、複数の出力様式へ変換する |

2ケースで**「読む側」と「書く側」**の両方を扱えるため、参加者の成果物が同じ方向に集まりません。3-2（運送会社）も候補でしたが、4システムの突き合わせという性質が3-3と重なるため外しました。

### 1-2　現場感とビジネス感の両方を、適度に持つ

ケースが現場に寄りすぎると「面白いが誰が金を払うのか」になり、ビジネスに寄りすぎると「現場が見えない机上の話」になります。3-1と3-3は、その両方を1つのケースの中に持っています。

| | 現場感 | ビジネス感 |
| --- | --- | --- |
| 3-1 | 製造ラインの合間にタブレット入力、油と水のある作業環境、パート従業員の入れ替わり | 取引先監査への対応、クレーム対応コスト、品質事故が起きたときの取引停止リスク |
| 3-3 | 畑からのLINE報告、夜に台所で入力、天候に左右される作業 | 出荷先3社との取引継続条件、GAP認証の維持、補助金の受給、労働時間の管理 |

どちらも、**「記録が楽になる」という現場の話が、そのまま「取引を失わない」「認証を維持する」という経営の話に直結**しています。スポンサーに提示したときに「うちの顧客の話だ」と受け取られる強度があり、同時に参加者は具体的な作業風景を想像できます。

### 1-3　データを用意しやすい

副次的な理由ですが、実務上は重要です。両ケースとも、**記録の様式が法令・認証で定まっている**ため、実データを使わなくても現実に近いダミーデータを設計できます。HACCPの記録項目、GAPの記録項目、行政の補助金様式は公開情報から構造を再現でき、「ありそうなデータ」ではなく「実際にその形で存在するデータ」を作れます。

## 2. ケース 3-1 の作り込み

### 2-1　舞台設定

| 項目 | 設定 |
| --- | --- |
| 会社 | 惣菜製造（社名は架空。仮に「ダミー食品」とし、配布時に決定） |
| 所在 | 地方都市の郊外、工業団地内の自社工場1棟 |
| 従業員 | 12名（代表1、製造リーダー1、製造パート8、配送2） |
| 製品 | 惣菜20品目（煮物、和え物、サラダ、揚げ物、炒め物） |
| 取引先 | 地域スーパー3社（計18店舗）、直売所2か所 |
| 売上 | 年商約2億円 |
| 認証 | HACCPに沿った衛生管理（義務化対応）。取引先による年2回の工場監査あり |

### 2-2　登場人物

| 人物 | 立場 | 困っていること |
| --- | --- | --- |
| 製造リーダー・佐藤（45歳） | 記録係を兼任。製造の中心 | 入力する時間はあるが、見返す時間がない。「記録のために記録している」感覚がある |
| 代表（61歳） | 経営全般、取引先対応 | 監査は通るが、クレームが減らない。原因が分からないまま「気をつけます」と謝っている |
| 製造パート（8名、勤続1か月〜15年） | 製造・入力の一部を担う | アプリの入力項目の意味が分からないまま、前回と同じ数字を入れることがある |
| 取引先の品質管理担当 | 年2回の監査を実施 | 記録の不備を指摘するが、記録が改善につながっているようには見えない |

### 2-3　1日の流れ（記録が発生するタイミング）

| 時刻 | 作業 | 発生する記録 |
| --- | --- | --- |
| 5:00 | 原材料受入 | 受入記録（品目・ロット・数量・受入温度・外観） |
| 5:30 | 従業員健康チェック | 健康記録（体温・体調・手指の傷） |
| 6:00〜8:00 | 加熱工程 | 加熱記録（製品・バッチ・中心温度・加熱時間） |
| 8:00〜9:00 | 冷却 | 冷却記録（開始/終了時刻・温度） |
| 9:00〜11:00 | 盛付・包装 | 製造日報（製造数・廃棄数・特記事項） |
| 11:00 | 出荷 | 出荷記録 |
| 15:00 | 清掃 | 清掃記録（区域別チェック） |
| 随時 | 冷蔵庫・冷凍庫 | 温度自動ログ（10分間隔、3台） |

### 2-4　すでに解決を試みたこと（＝なぜAIが必要か）

ケース文に含める前提です。これがあると「まずアプリを入れれば」という提案を封じられます。

- **3年前：手書きからHACCP記録アプリへ移行**した。監査対応は楽になり、PDFで過去分を提示できるようになった
- **アプリには一覧表示とCSV出力、閾値超過のアラート機能がある**。閾値超過は月に1〜2回鳴るが、「入力ミス」として訂正されることが多く、現場はアラートを信用していない
- **BIツールの導入を検討した**が、グラフを作っても「見て何をすればいいのか」が分からず、見積を取った段階で止まった
- **クレームが出るたびに原因を探る**が、該当日の記録を見ても異常値はなく、「原因不明」で終わっている

→ 記録は構造化されて溜まっているのに、**「どの記録とどの結果が結びついているか」を誰も追えていない**。ここがAIに問う価値のある部分です。

### 2-5　配布用ケース文（改訂版）

> スーパー向けの惣菜を作る、従業員12名の工場。3年前にHACCP記録アプリを導入し、原材料の受入温度、加熱の中心温度、冷却時間、清掃、従業員の健康チェックを、毎日タブレットで記録している。取引先の監査ではPDFを提示すれば済むようになり、指摘も減った。
>
> それでも、クレームは年に40件前後で変わらない。クレームが出るたび該当日の記録を見返すが、閾値を外れた数値は見つからず「原因不明」で終わる。記録係の製造リーダーは「入力する時間はあっても、見返す時間はない」と言い、代表は「2年分の記録が溜まっているのに、そこから何も分かっていない」と言う。
>
> 2年分の記録（約35万行）と、同期間のクレーム記録・微生物検査結果・監査指摘がある。**AIで何ができる？**
>
> *方向性：記録を減らすことが目的ではありません。現場の人が明日の作業を変えられる形で、記録から何かを取り出してください。判断は人が行います。*

## 3. ケース 3-3 の作り込み

### 3-1　舞台設定

| 項目 | 設定 |
| --- | --- |
| 法人 | 農業法人（社名は架空） |
| 所在 | 地方の平坦地。圃場は自宅から半径3km内に点在 |
| 従業員 | 9名（代表、代表の妻、息子、常勤3、パート3） |
| 圃場 | 12圃場（露地8・ハウス4）、計3.2ha |
| 作物 | トマト、きゅうり、ほうれん草、小松菜、ブロッコリー |
| 出荷先 | スーパー3社、JA、直売所2、EC（少量） |
| 売上 | 年商約6,000万円 |
| 認証 | JGAP（取得3年目）。年1回の審査あり |

### 3-2　登場人物

| 人物 | 立場 | 困っていること |
| --- | --- | --- |
| 代表の妻（52歳） | 事務・記録の一元担当 | 畑の作業が終わった夜に、LINEを見ながらアプリへ転記。提出のたびに様式ごとに書き直す |
| 代表（58歳） | 栽培管理・出荷交渉 | 「同じことを4回書いている。記録のせいで畑に出る時間が減っている」 |
| 息子（30歳） | 就農3年目。ECと販路開拓 | アプリのデータを販売に使いたいが、様式変換に追われる母を手伝う時間で消える |
| 常勤・パート（6名） | 作業実施。LINEで報告 | 報告の書き方は各自流。「A圃場」「Aハウス」「上の畑」が同じ場所を指す |
| 出荷先3社の品質担当 | 栽培履歴の提出を要求 | 各社別様式。不備があれば差し戻す |

### 3-3　記録が4回書き直される経路

```
畑（作業者6名）
  │ LINEグループに報告（テキスト＋写真、1日5〜15件）
  ▼
代表の妻（夜、台所）
  │ 目で読んで転記
  ▼
営農管理アプリ（JGAP対応・作業/農薬/肥料/収穫/出荷）
  │
  ├─→ ① JGAP審査用の記録（アプリから出力できる：唯一楽な経路）
  ├─→ ② スーパーA社「栽培履歴書」Excel：品目ごとに別シート、農薬は商品名、月単位
  ├─→ ③ スーパーB社「生産履歴」Excel：農薬は有効成分名で記載、収穫ロット単位
  ├─→ ④ スーパーC社：Web入力用CSV、農薬コード必須（同社のコード表に従う）
  └─→ ⑤ 補助金実績報告（行政様式）：作付面積・労働時間・販売金額、四半期単位
```

②〜⑤は、元が同じ作業記録なのに、**項目名・単位・集計期間・農薬の呼び方がすべて違う**ため、アプリの出力を見ながら手で作り直しています。

### 3-4　すでに解決を試みたこと

- **2年前に営農管理アプリを導入**した。JGAPの記録はこれで出せるようになった
- **アプリのCSV出力を使ってExcelマクロを作ろうとした**が、出荷先の様式が毎年少し変わるため、作ったマクロが1年で使えなくなり、やめた
- **作業者にアプリを直接入力させようとした**が、畑で手袋をしたまま項目を選ぶのが現実的でなく、LINE報告に戻った
- **農薬の商品名と有効成分名の対応表を自作した**が、新しい農薬を使うたびに更新が必要で、半年で放置された

→ 記録の入口（LINE）と出口（4つの様式）のあいだの変換が人力のまま。**非構造の報告を、複数の決まった形へ変換する**という、AIに向いた問題が残っています。

### 3-5　配布用ケース文（改訂版）

> 野菜を作る従業員9名の農業法人。作業者は畑からLINEグループに「A圃場 トマト 摘芯 3名 9:00-11:30」と写真付きで報告し、事務担当（代表の妻）が夜にそれを読んで営農管理アプリへ入力する。JGAPの記録はアプリから出せるようになった。
>
> しかし出荷先のスーパー3社は、それぞれ別のExcel様式で栽培履歴の提出を求める。A社は農薬を商品名で、B社は有効成分名で、C社は自社の農薬コードで書くよう指定してくる。集計単位も月・収穫ロット・作付とばらばらだ。補助金の実績報告は行政の様式で、労働時間の集計を求められる。どれも元は同じ作業記録なのに、様式ごとに手で書き直している。
>
> 代表は「同じことを4回書いている。記録のせいで畑に出る時間が減っている」と言う。
>
> 2年分のLINEログ（約7,000件・写真付き）、営農管理アプリのデータ、出荷先3社の様式と過去の提出物、補助金の実績報告がある。**AIで何ができる？**
>
> *方向性：提出をなくすことはできません。同じことを4回書かなくて済む形を考えてください。提出前の最終確認は人が行います。*
