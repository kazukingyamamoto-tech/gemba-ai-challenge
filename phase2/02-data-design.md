# 用意するデータの設計（ケース 3-1 / 3-3）

作成：bridge AI
前提：[`01-case-deepdive.md`](01-case-deepdive.md) で作り込んだ2ケースに対し、配布するダミーデータを設計する。どの型をどれだけ入れるかの方針は [`04-data-types.md`](04-data-types.md)。

> 専門用語（HACCP、JGAP、PHI など）は [`glossary.md`](../glossary.md) を参照。

## 1. 全体方針

| 方針 | 内容 |
| --- | --- |
| 完全合成 | 実企業のデータは使わない。全件をスクリプトで生成する。人名・社名・地名・圃場名はすべて架空 |
| 様式は実物準拠 | HACCP・JGAP・補助金様式の**項目構造**は公開情報に合わせ、値だけを合成する |
| 1・2段目を厚く | 表計算・SQLで扱える型（時系列・台帳・マスタ・外部データ・操作ログ・自由記述）だけで成功の形に届く量を入れる |
| 3・4段目は加点 | チャット・長文・手書き・音声・画像は、使わなくても届くが使うと遠くへ行ける位置に置く |
| 正解ラベルは入れない | 「この行が正解」「この原料が原因」という対応付けは与えない。精度を測らないため、置けば当てっこになる |
| 結果の記録は入れる | クレーム・不適合・差し戻しなど「いつ何が起きたか」は入れる。原因との紐付けはしない |
| 「難」を意図的に仕込む | 表記ゆれ・欠損・単位混在・時刻ずれ・様式差異を設計として入れる（後述 4.） |
| 「仕込んだ現象」を埋める | 発見可能だが自明でない事実を埋め込む。**採点には使わない**（後述 5.） |
| 生成スクリプトは非公開 | 仕込んだ現象の在処が分かるため、参加者には配布しない。運営内で保管 |
| 段階公開 | 事前に一部、当日に全量、審査用に別期間を保持（後述 6.） |


### LINEログの形式例

```json
{"ts":"2024-05-14 09:02","from":"パートC","text":"A圃場 トマト 摘芯 3名 9:00-11:30","files":[]}
{"ts":"2024-05-14 13:41","from":"常勤1","text":"上の畑、きゅうり誘引おわりました","files":["IMG_2214.jpg"]}
{"ts":"2024-05-14 16:05","from":"代表","text":"ダコニール撒いた B 500倍 だいたい100L","files":["IMG_2216.jpg"]}
{"ts":"2024-05-14 18:22","from":"パートA","text":"","files":["IMG_2219.jpg","IMG_2220.jpg"]}

```

- 2行目：圃場の別名（「上の畑」＝A圃場）
- 3行目：農薬を略称・圃場を1文字・使用量を概算で報告
- 4行目：本文なし、写真のみ。何の作業かは画像から読むしかない
- 5行目：ボイスメッセージのみ。文字起こしは配らない

## 4. 意図的に仕込む「使い方の難」

参加者が必ず突き当たる壁として、次を設計に組み込む。**README には「データには実際の現場と同様の不整合が含まれます」とだけ書き、具体は明かさない。**

### 3-1 惣菜工場

| 種類 | 具体 |
| --- | --- |
| 表記ゆれ | 製品名「ポテトサラダ／ポテサラ／Pサラダ」、担当者「佐藤／佐藤M／さとう」 |
| 単位混在 | 数量の kg / g / ケース / 本、温度の「8.2」「8.2℃」「8度」 |
| 欠損 | 受入温度の欠損 約7%、ロットNo欠損 約12%、繁忙日の清掃記録の未入力 |
| 時刻のずれ | 冷蔵庫ログはUTC、アプリ記録はJST。操作ログの端末TB-02は時刻が約3分進んでいる |
| 前工程との断絶 | 加熱記録の「使用原料ロット」が、受入記録のロットNo表記と一致しないものが 約20% |
| 丸め癖 | 中心温度が基準75℃に対し「75.0」「75.1」に不自然に集中（実測より記入習慣の反映） |
| 値の書き換え | 操作ログには修正前の値が残るが、台帳CSVには最終値しかない。両者を突き合わせないと訂正の実態が見えない |
| 自由記述 | 製造日報の特記事項、クレーム申立内容、不適合の内容が口語・略語まじり |
| 写真の紐付け | 受入写真200枚のうち約15%はファイル名がレコードと対応しない（撮ったが記録に貼らなかった） |
| 旧形式 | アプリ導入前6か月分が手書きPDFスキャン。書き手3名で癖が違う |

### 3-3 農業法人

| 種類 | 具体 |
| --- | --- |
| 圃場名の別名 | 「A圃場／Aハウス／上の畑／ハウス1」が同一。マスタに一部だけ記載 |
| 農薬名の3系統 | 商品名・有効成分名・現場略称が混在。B社様式は成分名、C社はコード必須 |
| コード表の不備 | C社の農薬コード表に、実際に使った農薬のうち3件が載っていない |
| 日付のずれ | LINE報告は作業当日、アプリ入力は夜または翌朝 → 1日ずれた記録が 約15% |
| 単位混在 | 収穫・出荷が kg / ケース / コンテナ / 本 で混在。ケースの入り数は出荷先ごとに違う |
| 伝票との不一致 | 出荷記録と請求データで数量が合わない行が 約3%（積み増し・返品・規格外の振替） |
| 労働時間の不在 | LINEには人数と時間帯があるが、アプリの作業記録に労働時間欄がない → 補助金報告は推計 |
| 写真だけの報告 | 本文なしで写真のみの投稿が 約8%。画像から作業を推定する必要がある |
| 音声だけの報告 | ボイスメッセージのみの投稿が30本。文字起こしは付けない |
| 様式の年次変更 | A社様式が2年目に列構成を変更。過去提出物は旧様式のまま |
| 過去の誤記 | B社への提出物に有効成分名の誤記が1件（差し戻し履歴と対応） |

## 5. 仕込んだ現象（運営用・非公開）

データから発見可能で、かつ気づけば現場の行動が変わる事実を埋め込む。

> **「正解」とは呼ばない。** 役割は**「このデータは解ける」ことを運営が保証するための自己検証**、これ1つだけ。採点表には載せない。参加者が1つも挙げなくても、別の筋で成功の形に届く理屈が立っていれば評価する。逆に全部当てても現場で使えない形なら評価しない。

### 3-1 惣菜工場

| # | 仕込む事実 | 発見の経路 | 段 |
| --- | --- | --- | --- |
| A | 特定仕入先の鶏肉ロットで、7〜9月の受入温度が基準上限付近に偏る。該当ロットを使った製品にクレームと不適合が集中 | 受入記録 × 加熱記録の原料ロット × クレームの推定製造日 | 1 |
| B | 製造数が上位10%の日に、冷却の所要時間が平均より30%長い。翌週の微生物検査値も高い傾向 | 製造日報 × 冷却記録 × 微生物検査 | 1 |
| C | 金曜午後の週次清掃が、月末の繁忙日に未入力になりやすい。その翌週に不適合が出る確率が上がる | 清掃記録の欠損パターン × 不適合記録 | 1 |
| D | 冷蔵庫1台が、2年目の秋以降に設定温度へ復帰する時間が延びている（劣化の兆候） | 温度自動ログの時系列 | 1 |
| E | 閾値アラートの約7割が「訂正」で閉じられ、その訂正が特定の担当者と早朝の時間帯に偏る | 操作ログ × 加熱記録 | 2 |
| F | 手書き期間の受入温度は、アプリ期間より分散が大きい（アプリ導入後に記録が均質化＝丸められている） | 手書きPDF × 受入記録 | 3 |
| G | 外観判定が「良」なのに、写真では変色が見えるものが数件ある。うち2件はのちにクレームへ | 受入写真 × 受入記録 × クレーム | 4 |

A〜Dが1段目で到達可能、E が2段目、F・G が3・4段目。**1段目だけで4つ見つかる設計**にしている。

### 3-3 農業法人

| # | 仕込む事実 | 発見の経路 | 段 |
| --- | --- | --- | --- |
| A | 収穫前日数（PHI）のニアミスが2件ある（違反ではないが余裕1日） | 農薬使用記録 × 収穫記録 × 農薬マスタ | 1 |
| B | 農薬使用回数が、1作物1シーズンの登録上限に達している組み合わせが1件ある | 農薬使用記録の集計 × マスタ | 1 |
| C | 提出物の作成に月あたり約14時間かかっており、その半分が様式Cへの転記に費われている | 操作ログのセッション分析 | 2 |
| D | 差し戻し5件のうち4件が、農薬名の系統違い（商品名と有効成分名の混同）に起因する | 差し戻し履歴 × 過去提出物 × 農薬マスタ | 2 |
| E | LINEにあるがアプリに転記されていない作業が 約4%。うち1件は農薬散布 | LINEログ × アプリ作業記録の差分 | 3 |
| F | 補助金報告の労働時間が、LINEから再計算すると 約12% 過少 | LINEログの人数・時間帯 × 提出済み報告 | 3 |

A・B が1段目、C・D が2段目、E・F が3段目。

## 8. 制作の段取り

| 手順 | 内容 | 留意点 |
| --- | --- | --- |
| 1 | マスタ設計（製品・原料・仕入先・圃場・作物・農薬・出荷先・従業員） | 全データの骨格。農薬マスタはPHIと使用回数上限の整合を取る |
| 2 | 正常系データの生成スクリプトを書く | 季節性・曜日性・繁忙期を反映させる。seed固定 |
| 3 | 操作ログを台帳から逆算して生成 | 台帳の各行に対して「誰がいつ入力したか」を矛盾なく作る。滞在秒数の分布が時間の実測の土台になる |
| 4 | 「仕込んだ現象」を注入 | 統計的に検出可能だが、単純な閾値では出ない強度に調整する |
| 5 | 「難」（表記ゆれ・欠損・時刻ずれ）を注入 | 注入率を記録し、仕込んだ現象の発見可能性を潰さないか確認 |
| 6 | 自由記述とチャットの作成 | 3-1の日報特記500件・不適合400件・LINE 1,500件、3-3のLINE 7,000件。**合計約9,000件で最も時間がかかる工程** |
| 7 | 様式ファイルと過去提出物の作成 | 3-3の4様式。年次変更と誤記を反映 |
| 8 | 手書き・写真・音声の作成 | 手書き330枚、写真490枚、音声65分。書き手・撮影条件・話者を分ける |
| 9 | 自己検証 | 運営側で仕込んだ現象（3-1は7件、3-3は6件）が実際に発見できるかを、想定解法で一度通す |
| 10 | data_dictionary と starter の作成 | 参加者が30分でデータを読み始められる状態にする |

手順6が最大の山になる。**約9,000件の自然な日本語**の品質が、データ全体の説得力を決める。

### 要検討事項

| 論点 | 選択肢 |
| --- | --- |
| 写真490枚の調達 | 合成画像 / 自社撮影 / ライセンス素材。生成画像を使う場合は農薬容器のラベルなど実在ブランドが写らないようにする |
| 農薬名の扱い | 実在の農薬名を使うと現実味が増すが、記載内容の正確性に責任が生じる。架空の農薬名＋架空の登録内容にする案もある |
| 手書き330枚の作り方 | 実際に手書きして撮影する / 手書き風フォントで生成する |
| 音声65分の作り方 | 読み上げ音声を合成する / 実際に録音する。周囲の音（畑の風、工場の機械音）を重ねるか |
| 舞台の寄せ方 | 協賛企業が決まった場合、その顧客業種に舞台を寄せるか。寄せると狙いが露見するため、原則寄せない |
