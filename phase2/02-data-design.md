## 1. 全体方針

| 方針 | 内容 |
| --- | --- |
| 完全合成 | 実企業のデータは使わない。全件をスクリプトで生成する。人名・社名・地名・圃場名はすべて架空 |
| 様式は実物準拠 | HACCP・JGAP・補助金様式の**項目構造**は公開情報に合わせ、値だけを合成する |
| 「難」を意図的に仕込む | 表記ゆれ・欠損・単位混在・時刻ずれ・様式差異を設計として入れる（後述 4.） |
| 「隠された正解」を仕込む | データ内に、発見可能だが自明でない事実を埋め込む。審査基準に使う（後述 5.） |
| 生成スクリプトは非公開 | 正解を含むため、参加者には配布しない。運営内で保管 |
| 段階公開 | 事前に一部、当日に全量、審査用に別期間を保持（後述 6.） |

## 4. 意図的に仕込む「使い方の難」

参加者が必ず突き当たる壁として、次を設計に組み込みます。**README には「データには実際の現場と同様の不整合が含まれます」とだけ書き、具体は明かしません。**

**3-1（惣菜工場）**

| 種類 | 具体 |
| --- | --- |
| 表記ゆれ | 製品名「ポテトサラダ／ポテサラ／Pサラダ」、担当者「佐藤／佐藤M／さとう」 |
| 単位混在 | 数量の kg / g / ケース / 本、温度の「8.2」「8.2℃」「8度」 |
| 欠損 | 受入温度の欠損 約7%、ロットNo欠損 約12%、繁忙日の清掃記録の未入力 |
| 時刻のずれ | 冷蔵庫ログはUTC、アプリ記録はJST。さらに温度ログに通信断による欠測が散在 |
| 前工程との断絶 | 加熱記録の「使用原料ロット」が、受入記録のロットNo表記と一致しないものが 約20% |
| 丸め癖 | 中心温度が基準75℃に対し「75.0」「75.1」に不自然に集中（実測より記入習慣の反映） |
| 自由記述 | 製造日報の特記事項、クレームの申立内容が口語・略語まじり |
| 旧形式 | アプリ導入前6か月分が手書きPDFスキャン（OCRが必要） |

**3-3（農業法人）**

| 種類 | 具体 |
| --- | --- |
| 圃場名の別名 | 「A圃場／Aハウス／上の畑／ハウス1」が同一。マスタに一部だけ記載 |
| 農薬名の3系統 | 商品名・有効成分名・現場略称が混在。B社様式は成分名、C社はコード必須 |
| コード表の不備 | C社の農薬コード表に、実際に使った農薬のうち3件が載っていない |
| 日付のずれ | LINE報告は作業当日、アプリ入力は夜または翌朝 → 1日ずれた記録が 約15% |
| 単位混在 | 収穫・出荷が kg / ケース / コンテナ / 本 で混在。ケースの入り数は出荷先ごとに違う |
| 労働時間の不在 | LINEには人数と時間帯があるが、アプリの作業記録に労働時間欄がない → 補助金報告は推計 |
| 写真だけの報告 | 本文なしで写真のみの投稿が 約8%。画像から作業を推定する必要がある |
| 様式の年次変更 | A社様式が2年目に列構成を変更。過去提出物は旧様式のまま |
| 過去の誤記 | B社への提出物1件に、有効成分名の誤記がある（当時は差し戻されている） |

## 5. 仕込む「隠された正解」（運営用・非公開）

データから発見可能で、かつ気づけば現場の行動が変わる事実を埋め込みます。

> **役割の変更（2026-09-26）**：当初は「いくつ見つけられたか」を審査に使う想定でしたが、それでは正解探しの競争になり、アプローチの幅が失われます（→ [`01-case-deepdive.md` 1-4](01-case-deepdive.md#1-4成功の形は方向性で競えるように書く)）。
> 現在の役割は**「このデータは解ける」ことを運営が保証するための自己検証**です。採点表には載せません。参加者が正解を1つも挙げなくても、別の筋で成功の形に届く理屈が立っていれば評価します。

**3-1**

| # | 仕込む事実 | 発見の経路 |
| --- | --- | --- |
| A | 特定仕入先の鶏肉ロットで、7〜9月の受入温度が基準上限付近に偏る。該当ロットを使った製品にクレームが集中 | 受入記録 × 加熱記録の原料ロット × クレームの推定製造日 |
| B | 製造数が上位10%の日に、冷却の所要時間が平均より30%長い。翌週の微生物検査値も高い傾向 | 製造日報 × 冷却記録 × 微生物検査 |
| C | 金曜午後の週次清掃が、月末の繁忙日に未入力になりやすい。その翌週にクレームが出る確率が上がる | 清掃記録の欠損パターン × クレーム日付 |
| D | 中心温度の「75.0／75.1」への集中が、特定の担当者・特定の時間帯に偏る（記録の信頼性の問題） | 加熱記録の分布分析 |
| E | 冷蔵庫1台が、2年目の秋以降に設定温度へ復帰する時間が延びている（劣化の兆候） | 温度自動ログの時系列 |

**3-3**

| # | 仕込む事実 | 発見の経路 |
| --- | --- | --- |
| A | 収穫前日数（PHI）のニアミスが2件ある（違反ではないが余裕1日） | 農薬使用記録 × 収穫記録 × 農薬マスタの登録内容 |
| B | 農薬使用回数が、1作物1シーズンの登録上限に達している組み合わせが1件ある | 農薬使用記録の集計 × マスタ |
| C | LINEにあるが、アプリに転記されていない作業が 約4%。うち1件は農薬散布 | LINEログ × アプリ作業記録の差分 |
| D | 補助金報告の労働時間が、LINEから再計算すると 約12% 過少 | LINEログの人数・時間帯 × 提出済み報告 |
| E | B社への過去提出物に有効成分名の誤記が1件（差し戻し履歴と対応） | 過去提出物 × 農薬マスタ × JGAP記録 |

## 6. 公開の段階

| 段階 | 時期 | 内容 |
| --- | --- | --- |
| ① サンプル公開 | 募集開始時 | 各ケース1〜2か月分（全体の約10%）。参加者が事前に構造を掴み、環境を準備できる |
| ② 全量公開 | 開催当日 | 2年分。隠された正解はこの範囲に含む |
| ③ ホールドアウト | 審査時のみ | ①②に含まない別の3か月分。成果物をこのデータに当てて動くかを確認 |

③を用意することで、当日のデータに合わせ込んだだけの成果物と、実際に使えるものを区別できます。

## 7. 同梱する補助物

- `README.md`：データの全体像、ファイル一覧、利用上の注意（不整合が含まれる旨）
- `data_dictionary.md`：全ファイルの列定義、値の意味、単位、欠損の扱い
- `starter.ipynb`：全ファイルを読み込み、件数と欠損率を表示するところまでのサンプル（UMP-JUSTが三菱電機ケースでサンプルコードを配ったのと同じ趣旨。技術的な立ち上がりで差がつかないようにする）
- `formats/` の空様式：3-3で提出物を生成する場合の出力先
- ライセンス表記：合成データであること、コンテスト外での利用条件

## 8. 制作の段取り

| 手順 | 内容 | 留意点 |
| --- | --- | --- |
| 1 | マスタ設計（製品・原料・仕入先・圃場・作物・農薬・従業員） | ここが全データの骨格。農薬マスタは実在の登録内容を参照して整合を取る |
| 2 | 正常系データの生成スクリプトを書く | 季節性・曜日性・繁忙期を反映させる。seed固定 |
| 3 | 「隠された正解」を注入 | 統計的に検出可能だが、単純な閾値では出ない強度に調整する |
| 4 | 「難」（表記ゆれ・欠損・時刻ずれ）を注入 | 注入率を記録し、正解の発見可能性を潰さないか確認 |
| 5 | 非構造データの作成 | 3-1の自由記述・手書きPDF、3-3のLINE本文・写真。写真は合成画像かライセンスの明確な素材を使う |
| 6 | 様式ファイルと過去提出物の作成 | 3-3の4様式。年次変更と誤記を反映 |
| 7 | 自己検証 | 運営側で5つの正解が実際に発見できるかを、想定解法で一度通す |
| 8 | data_dictionary と starter の作成 | 参加者が30分でデータを読み始められる状態にする |

**要検討事項**

- 写真250枚の調達方法（合成画像 / 自社撮影 / ライセンス素材）。生成画像を使う場合は農薬容器のラベルなど実在ブランドが写らないようにする
- 農薬マスタに実在の農薬名を使うかどうか。使うと現実味が増すが、記載内容の正確性に責任が生じる。架空の農薬名＋架空の登録内容にする案もある
- スポンサーが決まった場合、そのスポンサーの顧客業種に舞台を寄せるか（寄せると狙いが露見するため、原則寄せない）
