# 配布データの方針

bridge AI

どの型をどれだけ入れるか、どう作るか、いつ公開するか。**3案に共通する方針**で、案ごとのファイル定義は各ケースのファイルにある。

> 専門用語は [`../glossary.md`](../glossary.md) を参照。

---

## 全体方針

| 方針 | 内容 |
| --- | --- |
| 完全合成 | 実企業のデータは使わない。全件をスクリプトで生成する。人名・社名・地名・圃場名はすべて架空 |
| 様式は実物準拠 | HACCP・JGAP・補助金様式の**項目構造**は公開情報に合わせ、値だけを合成する |
| 1・2段目を厚く | 表計算・SQLで扱える型（時系列・台帳・マスタ・外部データ・操作ログ・自由記述）だけで成功の形に届く量を入れる |
| 3・4段目は加点 | チャット・長文・手書き・音声・画像は、使わなくても届くが使うと遠くへ行ける位置に置く |
| 正解ラベルは入れない | 「この行が正解」「この原料が原因」という対応付けは与えない。精度を測らないため、置けば当てっこになる |
| 結果の記録は入れる | クレーム・不適合・差し戻しなど「いつ何が起きたか」は入れる。原因との紐付けはしない |
| 「難」を意図的に仕込む | 表記ゆれ・欠損・単位混在・時刻ずれ・様式差異を設計として入れる。具体は各ケースのファイル |
| 「仕込んだ現象」を埋める | 発見可能だが自明でない事実を埋め込む。**採点には使わない**（後述「『仕込んだ現象』の位置づけ」） |
| 生成スクリプトは非公開 | 仕込んだ現象の在処が分かるため、参加者には配布しない。運営内で保管 |
| 段階公開 | 事前に一部、当日に全量、審査用に別期間を保持（後述「公開の段階」） |

## データ型の一覧

現場に存在しうるデータを、何で表現されているか（モダリティ）で切ると12種類に収まる。

| 型 | 中身 | 生成元 |
| --- | --- | --- |
| ① 計測値の時系列 | 冷蔵庫温度、WBGT、ナースコール | 機械が自動記録 |
| ② 台帳レコード | 受入記録、農薬使用記録、勤怠、シフト | 人が様式に入力 |
| ③ イベントログ | アプリ操作履歴、レジ取消、打刻 | システムが吐く |
| ④ 短文の自由記述 | 日報の特記事項、クレーム申立、ヒヤリハット | 人が欄に書いた |
| ⑤ 長文の文書 | BCP本体、監査報告書、規程、協定書 | 人が作った文書 |
| ⑥ チャットログ | LINE、店長グループ、申し送り | 会話の流れ |
| ⑦ 音声 | 通話録音、ボイスメッセージ、聞き取り | 人が話した |
| ⑧ 画像 | 原料・商品・売場・設備の写真、図面 | 人が撮った・描いた |
| ⑨ スキャン・手書き | 紙記録のPDF、手書きの振り返りシート | 紙をデジタル化 |
| ⑩ 様式・テンプレート | 提出用Excel、行政様式、コード表 | 提出先が定めた器 |
| ⑪ マスタ・参照データ | 農薬マスタ、製品マスタ、店舗マスタ | 台帳の背骨 |
| ⑫ 外部データ | 気象、地図、商圏統計、ハザードマップ | 外から持ってくる |

## 技術レベルの4段

難易度を決めているのはモダリティよりも**結合キーが壊れているかどうか**だが、入口として必要な技術で並べると次のようになる。

| 段 | 型 | 入口の技術 |
| --- | --- | --- |
| **1段目** | ①②⑪⑫ | 表計算・SQL・基本的な統計 |
| **2段目** | ④⑩③ | LLMでテキストを構造化する、様式へ写す |
| **3段目** | ⑥⑤⑨ | 文脈と長文を扱う。省略・口語・手書きに耐える |
| **4段目** | ⑦⑧ | 音声・画像。前処理そのものが一仕事 |

## 厚みの置き方

**1・2段目を厚くし、3・4段目は加点に置く。**

| | 置き方 |
| --- | --- |
| 1・2段目 | これだけで成功の形に**届く**量と質を入れる。どのチームも初日に何か言える状態を作る |
| 3・4段目 | 使わなくても届くが、**使うと明確に遠くへ行ける**。必須にはしない |

3・4段目を必須にすると技術レベルの低いチームが詰み、飾りで足すとノイズになる。避けるべきはその両方で、狙うのは「1・2段目で立てた仮説を、3・4段目で裏づけられる／覆せる」という関係。各ケースの末尾に、この2段構えを明示する。

## 入れないもの、入れるもの

| | 扱い |
| --- | --- |
| **正解ラベル** | **入れない。** 「この行が正解」「この原料が原因だ」という対応付けは与えない。精度を測らないコンテストで正解を置けば、当てっこになる |
| **結果の記録** | **入れる。** 「いつ、何が起きたか」の羅列のみ。原因との紐付けはしない |

結果の記録を入れるのは、審査基準②「その方向で数字が動く理屈が立っているか」がこれなしに機能しないため。「この仕入先の受入温度が夏場に高い」と見つけても、クレーム記録がなければそれが何なのか誰も言えない。あれば「過去40件のうち何件がこの筋に当たる」と言える。精度の話ではなく、**主張に足場があるか**の話であり、独創性を評価したいときほど比較の土台は必要になる。

なお、現実の会社にはクレーム記録も退職者記録も必ず残っている。外すほうが不自然でもある。

必要度は成功の形のタイプで分かれる。

| タイプ | ケース | 結果の記録 |
| --- | --- | --- |
| 業務量・時間を減らす | 農業法人（月25時間→半分） | 薄くてよい。削るべき作業がデータにそのまま存在する |
| 悪いことの発生を減らす | 惣菜工場（クレーム年40件→減） | **必要**。減らす対象がデータにないと空中戦になる |

## 「仕込んだ現象」の位置づけ

データには、発見可能だが自明でない現象を意図的に埋め込む。ただしこれを**正解とは呼ばない**。役割は次の1つだけ。

> **運営が「このデータは解ける」と保証するための自己検証。**

採点表には載せない。参加者が1つも挙げなくても、別の筋で成功の形に届く理屈が立っていれば評価する。逆に全部当てても現場で使えない形なら評価しない。

## 重い型（⑦音声・⑧画像・⑨手書き）の分量方針

生成負荷が高いため、各ケース共通の上限を設ける。

| 型 | 方針 |
| --- | --- |
| ⑦ 音声 | **実音声は1ケース30〜40分に絞る。** 音声処理を体験できる量は確保し、量で殴る展開は避ける |
| ⑧ 画像 | 1ケース200〜300枚。合成画像かライセンスの明確な素材を使い、実在ブランドが写らないようにする |
| ⑨ スキャン・手書き | 1ケース100〜200枚。手書きは書き手ごとに癖を変える |

## 公開の段階

| 段階 | 時期 | 内容 |
| --- | --- | --- |
| ① サンプル公開 | 募集開始時 | 各ケース1〜2か月分（全体の約10%）。参加者が事前に構造を掴み、環境を準備できる |
| ② 全量公開 | 開催当日 | 2年分。仕込んだ現象はこの範囲に含む |
| ③ 別期間データ | 審査時のみ | ①②に含まない別の3か月分。**軽い扱い**とする。精度を測らないため過学習を疑う必要は薄く、「別の期間でも動くか」の確認に留める |

## 同梱する補助物

| ファイル | 内容 |
| --- | --- |
| `README.md` | データの全体像、ファイル一覧、利用上の注意（不整合が含まれる旨） |
| `data_dictionary.md` | 全ファイルの列定義、値の意味、単位、欠損の扱い |
| `starter.ipynb` | 全ファイルを読み込み、件数と欠損率を表示するところまでのサンプル。技術的な立ち上がりで差がつかないようにする |
| `formats/` の空様式 | 3-3で提出物を生成する場合の出力先 |
| ライセンス表記 | 合成データであること、コンテスト外での利用条件 |

`starter.ipynb` を配る狙いは、UMP-JUST が三菱電機ケースでサンプルコードを配ったのと同じ。**参加者が30分でデータを読み始められる状態**にする。

## 制作の段取り

| 手順 | 内容 | 留意点 |
| --- | --- | --- |
| 1 | マスタ設計（製品・原料・仕入先・圃場・作物・農薬・出荷先・従業員） | 全データの骨格。農薬マスタはPHIと使用回数上限の整合を取る |
| 2 | 正常系データの生成スクリプトを書く | 季節性・曜日性・繁忙期を反映させる。seed固定 |
| 3 | 操作ログを台帳から逆算して生成 | 台帳の各行に対して「誰がいつ入力したか」を矛盾なく作る。滞在秒数の分布が時間の実測の土台になる |
| 4 | 「仕込んだ現象」を注入 | 統計的に検出可能だが、単純な閾値では出ない強度に調整する |
| 5 | 「難」（表記ゆれ・欠損・時刻ずれ）を注入 | 注入率を記録し、仕込んだ現象の発見可能性を潰さないか確認 |
| 6 | 自由記述とチャットの作成 | 3-1の日報特記500件・不適合400件・LINE 1,500件、3-3のLINE 7,000件。**合計約9,000件で最も時間がかかる工程** |
| 7 | 様式ファイルと過去提出物の作成 | 3-3の4様式。年次変更と誤記を反映 |
| 8 | 手書き・写真・音声の作成 | 手書き330枚、写真490枚、音声65分。書き手・撮影条件・話者を分ける |
| 9 | 自己検証 | 運営側で仕込んだ現象（3-1は7件、3-3は6件）が実際に発見できるかを、想定解法で一度通す |
| 10 | data_dictionary と starter の作成 | 参加者が30分でデータを読み始められる状態にする |

手順6が最大の山になる。**約9,000件の自然な日本語**の品質が、データ全体の説得力を決める。

## 生成負荷と着手順

| 優先 | 対象 | 理由 |
| --- | --- | --- |
| 1 | 両ケースのマスタ設計（⑪） | 全データの骨格。ここが決まらないと他が作れない |
| 2 | 1段目の①②⑫ | 量は多いがスクリプトで機械的に生成できる |
| 3 | 2段目の③⑩ | 操作ログは行数が多いが生成は単純。様式は実物構造の再現に手間がかかる |
| 4 | 2・3段目の④⑥ | 自由記述とチャットは1件ずつ質を作る必要があり、最も時間がかかる |
| 5 | 3段目の⑤⑨ | 文書は点数が少ない。手書きスキャンは書き手の癖を分ける手間 |
| 6 | 4段目の⑦⑧ | 音声30〜40分・画像240〜250枚。素材調達の判断が先に必要 |

**④と⑥が最大の山**になる。惣菜工場のLINE 1,500件と日報特記500件、農業法人のLINE 7,000件。**合計約9,000件**の自然な日本語を作る必要があり、ここの品質がデータの説得力を決める。

4ケース構成だった時点では2万件超だったので、2本に絞ったことで**生成負荷はおよそ半分以下**になった。音声と画像も、4ケース分（音声2時間超・画像700枚超）から2ケース分（音声65分・画像490枚）に下がる。

## 要検討事項

| 論点 | 選択肢 |
| --- | --- |
| 写真の調達 | 合成画像 / 自社撮影 / ライセンス素材。生成画像を使う場合は、農薬容器のラベルや商品パッケージなど実在ブランドが写らないようにする |
| 農薬名の扱い | 実在の農薬名を使うと現実味が増すが、記載内容の正確性に責任が生じる。架空の農薬名＋架空の登録内容にする案もある |
| 手書きの作り方 | 実際に手書きして撮影する / 手書き風フォントで生成する。いずれも書き手ごとに癖を分ける |
| 音声の作り方 | 読み上げ音声を合成する / 実際に録音する。周囲の音（畑の風、工場の機械音、店内放送）を重ねるか |
| センシティブな内容の強度 | SaaS案（カスハラ対策）で扱う事例の生々しさをどこまで出すか。強度を3段階に分け、重度は1割に絞る方針 |
| 舞台の寄せ方 | 協賛企業が決まった場合、その顧客業種に舞台を寄せるか。寄せると狙いが露見するため、原則寄せない |
