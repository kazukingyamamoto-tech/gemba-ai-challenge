## 1. 3案目を作った理由

惣菜工場と農業法人の2案を作り終えた段階で、2つの違和感が残りました。

**1つは、業界が学生に届いていないこと。** 「ビジネス×AIってどんなだろう」とワクワクして来た学生に、惣菜屋や農家の話をしても納得感が薄いのではないか。ケース文の書き方（二人称・数字先出し）では工夫できましたが、**業界そのものはターゲット層に届いていない**という懸念が消えませんでした。

**もう1つは、回答の広がりが浅いこと。** 今回のコンテストは精度ではなく方向性を評価するはずです。ところが既存2案は、HACCPの「中心温度75℃で1分以上」、JGAPの「PHI・使用回数の上限」のように**法令で基準が決まっている**ため、どう書いても「決まった基準に対して違反を見つける」競争に引っぱられます。

そこで、**SaaS企業のカスタマーサクセス**を舞台に、カスハラ対策を題材とした3案目を作りました。小売・食品の現場ではなく、**学生の志望業界と重なる場所**を選んでいます。理由は3つです。

| # | 理由 |
| --- | --- |
| ① | **新鮮さとタイムリーさ。** 2026年10月1日施行で、企業として早急な対応が必要な状況そのものが「ビジネス現場」感を持っている |
| ② | **アイデアの広がり。** 相談窓口という「うまく機能していないしくみ」をAIで組み直す題材。加えて**カスハラをしてくる相手が契約者＝売上源**なので、本物のトレードオフがある |
| ③ | **協賛企業へのインパクト。** 対象が労働者を1人でも雇う全事業主。協賛企業も審査員も自社で対応しなければならない立場にある |

## 3. ケースA　惣菜工場

### 背景

**HACCP**（危害要因分析・重要管理点）は、食品の製造工程のうち危険が起こりうる箇所を特定し、継続的に監視・記録する衛生管理の手法。**2021年6月から原則すべての食品事業者に義務化**された。惣菜製造では受入温度、加熱の中心温度（**75℃で1分以上**）、冷却時間が重要管理点で、毎回の記録が必須。取引先のスーパーは年2回ほど工場を訪れて記録の提示を求め、**指摘が続けば取引停止につながる**。

### ケース文

> あなたは、スーパー向けの惣菜を作る従業員12名の工場の代表です。
>
> クレームは年に40件。3年前にHACCP記録アプリを導入し、原材料の受入温度、加熱の中心温度、冷却時間、清掃、従業員の健康チェックを毎日タブレットで記録するようにしました。取引先の監査ではPDFを提示すれば済むようになり、指摘も減りました。それでもクレームの件数は、導入前と変わっていません。
>
> クレームが出るたび、あなたは該当日の記録を見返します。しかし閾値を外れた数値は見つからず、毎回「原因不明」で終わります。取引先には「以後気をつけます」と伝えるしかありません。次の監査は2か月後です。
>
> 記録係を兼ねる製造リーダーは「入力する時間はあっても、見返す時間はない」と言います。手元には2年分の記録が約39万行。クレーム記録、社内の不適合記録、微生物検査結果、監査指摘、受入時とクレーム時の写真、アプリ導入前の手書き記録も残っています。
>
> **さて、AIを使って何をしますか？**
>
> **成功の形：クレームを年40件から減らす。ただし記録にかける時間は増やさない。**
>
> *方向性：記録を減らすことが目的ではありません。判断は人が行います。*

## 4. ケースB　農業法人

### 背景

**GAP**（農業生産工程管理）は、食品安全・環境保全・労働安全の観点から農作業の手順を定めて記録する取り組み。日本発の認証が**JGAP**で、大手小売の取引条件として求められることが増えている。農薬には**PHI（収穫前日数）**と**使用回数の上限**がラベルで定められ、違反すると出荷停止や認証取消につながる。さらに同じ有効成分でもメーカーによって商品名が異なるため、「商品名で書くか、有効成分名で書くか」が提出先ごとに分かれる。栽培履歴の様式も出荷先ごとに違う。

### ケース文

> あなたは、野菜を作る従業員9名の農業法人の代表です。
>
> 記録と提出にかけている時間は、月に25時間を超えます。作業者は畑からLINEグループに「A圃場 トマト 摘芯 3名 9:00-11:30」と写真付きで報告し、事務を担う妻が夜にそれを読んで営農管理アプリへ入力します。JGAPの記録はアプリから出せるようになりました。
>
> ところが出荷先のスーパー3社は、それぞれ別のExcel様式で栽培履歴の提出を求めます。A社は農薬を商品名で、B社は有効成分名で、C社は自社の農薬コードで書くよう指定してきます。集計単位も月・収穫ロット・作付とばらばらです。補助金の実績報告は行政の様式で、労働時間の集計を求められます。どれも元は同じ作業記録なのに、様式ごとに手で書き直しています。去年は誤記で1件差し戻され、出荷先から改善を求められました。来月末には、A社への提出と四半期の補助金報告が重なります。
>
> 同じことを4回書いている、とあなたは思っています。記録のせいで、畑に出る時間が減っています。
>
> 手元には2年分のLINEログが約7,000件（写真とボイスメッセージ付き）、営農管理アプリのデータと操作ログ、出荷先3社の様式と過去の提出物、差し戻しの履歴、補助金の実績報告、アプリ導入前の手書き日誌があります。
>
> **さて、AIを使って何をしますか？**
>
> **成功の形：記録と提出にかかる時間（月約25時間）を半分にし、提出物の差し戻しをゼロにする。**
>
> *方向性：提出をなくすことはできません。提出前の最終確認は人が行います。*

## 5. ケースC　SaaS企業のカスタマーサクセス（カスハラ対策）

### 背景

**2026年10月1日から、カスタマーハラスメント対策が全事業主の義務**となった（改正労働施策総合推進法）。労働者を1人でも雇う事業主が対象で、企業規模・業種による適用除外はない。

カスハラは「**顧客等**の言動であって、社会通念上許容される範囲を超えたものにより、労働者の就業環境が害されるもの」と定義される。ここでいう顧客等には**取引の相手方も含まれる**ため、**B2Bの取引先からのハラスメントも対象**になる。カスハラを「客が店員に怒鳴る」こととだけ捉えていると見落とす部分である。

事業主には、方針の明確化、**相談体制の整備**、事後の適切な対応、抑止のための措置が求められる（厚労省の防止指針は2026年2月告示、10項目）。ただし「社会通念上許容される範囲」に数値基準はなく、**どこからがカスハラかの線引きは各社に委ねられている**。

SaaS事業では、カスハラをしてくる相手が**契約者であり売上源**である。取引の見直しは法的に取りうる措置だが、それは解約と直結する。

### ケース文

**このケースは課題発見型です。** 解くべき課題と成功の形を、こちらで決めません。参加者がデータから見つけて定義します。

> あなたは、中小企業向けの業務SaaSを提供する従業員180名の会社で、カスタマーサクセスを統括しています。契約は1,200社、CS部門は35名です。
>
> 今年の春、カスハラ対策の義務化を見据えて、相談窓口を設け、方針を掲示し、エスカレーションルールを定めました。一次対応にはAIチャットボットも入れました。10月に法律が施行され、設置から半年あまりが経ちます。
>
> **措置は満たしています。** 窓口はあり、方針はあり、ルールもある。監督署から指摘を受ける状態ではありません。
>
> 窓口に上がってきた相談は、14件です。
>
> その数が多いのか少ないのか、あなたには判断がつきません。カスハラが起きていないならそれでいい。起きているのに上がってきていないなら、窓口は機能していないことになります。どちらなのかを示すものを、あなたは持っていません。
>
> 手元にあるのは、2年分の記録です。サポートチケットが約8万件（本文と社内メモ込み）、顧客との共有Slackチャネルが約3.5万件、プロダクトの利用ログが約88万行。契約・更新・解約の記録、CSメンバーの稼働ログと勤怠、在職者の意識調査と退職面談の記録、顧客満足度の回答、電話と会議の録音、顧客から届いたエラー画面のスクリーンショット。どれも、何かのために取られて、そのまま置かれています。
>
> 来月の経営会議で、窓口を設けてからの半年について報告することになっています。
>
> **さて、このデータを見て、何が問題だと考えますか。そしてAIを使って何をしますか？**
>
> **提出するもの**：①設定した課題とその根拠　②定義した成功の形とその測り方　③アプローチと動くもの
>
> *方向性：守るのは働く人です。従業員を監視したり、担当者の評価に使う道具にはしないでください。顧客との取引を見直すことは選択肢に入りますが、「この顧客は危険」と機械が一方的に決める形は求めていません。判断は人が行います。*
>
> *なお、この制度は2つの失敗を同時に禁じています。労働者を守らないことと、**正当な苦情をカスハラと決めつけて抑圧すること**です。どちらにも倒れない線の引き方を考えてください。*

### なぜ課題を示さないのか

「離職率が高い」「解約が怖い」といった課題意識を書けば、それが唯一の課題になります。施行直後の企業は、まさに「措置は満たしたが、何が起きているか分からない」状態にいます。**その状態をそのまま渡すのが、最も正直で、最も広がりのあるケースになります。**

データには離職記録も在職者意識調査も解約記録も製品の利用ログも入っています。離職に着目したいチームも、製品の分かりにくさに着目したいチームも、そこへ行けます。**どこに着目するかの判断が、最初の勝負になります。**

### 審査の順序（このケースの場合）

| 順位 | 見るもの |
| --- | --- |
| **1** | **どんな課題と成功の形を立てたか。** データの何を根拠にそう決めたか |
| 2 | アプローチの筋。その課題に対して、なぜその方向を選んだか |
| 3 | 効き方の理屈。自分で立てた成功の形に、その方向が効く筋道があるか |
| 4 | 実装の完成度 |

チームごとに成功の形が違っても、**「自分で引いたハードルの高さと、それを越えた度合い」**を見るので審査は成立します。低いハードルを選んだチームは1で負けます。

## 6. 3つの観点での比較

ケースの型や成功の形の書き方（手段を表す語を使わない、2条件にする、など）は3案とも共通の基準で作ってあります。**そこは差になりません。** 差が出るのは次の3点です。

### ① 学生への届き方

| | 評価 | 理由 |

## 7. 各案の弱点と、対処の見込み

### A 惣菜工場

| 弱点 | 対処 |
| --- | --- |
| 業界が学生に遠い | ケース文の語り口では改善したが、**業界そのものは変えられない** |
| 「75℃で1分以上」という基準があるため、検出の精度競争に引っぱられる | 成功の形を「クレームを減らす」に置いて緩和しているが、構造的な引力は残る |

### B 農業法人

| 弱点 | 対処 |
| --- | --- |
| 構造化データが約4万行で最少。分析し甲斐に欠ける | 操作ログ1.6万行を足して「現状の作業時間を実測する」という筋を作った |
| 課題が具体的すぎて、全チームが様式変換を作る可能性 | 成功の形を「時間半減＋差し戻しゼロ」の2条件にして経路を増やした |

### C SaaS企業

| 弱点 | **データ側での対処** |
| --- | --- |
| **効果測定が難しい**（離職の真因が追えない） | **解約記録140社と在職者の意識調査（匿名・年2回・4回分）を入れる。** 個人の因果は追えないが、回次単位・部門単位で比較でき、**離職と解約の両条件を同時に測れる** |
| データ量が多く初動が重い | 構造化データは約130万行で**3案中最多**。全ファイルを読み込むサンプルコードを同梱し、1段目だけで到達できる発見を3つ用意した |
| **課題発見型のため、1日目で止まるチームが出る** | 事前プログラムでサンプルデータを配り、構造を掴んだ状態で当日に入らせる。Day1午後の中間フィードバックで「どんな課題を立てたか」を全チームに言わせ、立てられていないチームをその場で引き上げる |
| **課題が制度から外れる方向へ流れる** | 「チケット対応を速くする」はサポート改善であってカスハラ対策ではない。方向性の但し書きと中間フィードバックで軌道を戻す |
| 全チームが相談AIを作るリスク | **窓口の記録を14件のまま薄く保つことが設計。** 窓口だけ見ても何もできない。材料は窓口の外（チケット8万件・社内メモ1.2万件・Slack 3.5万件・利用ログ88万行）に圧倒的に置く |
| センシティブさ | 事例の強度を3段階に分け、重度は1割に絞る。**暴力・性的な内容は含めない。** 配布物の冒頭に扱いの注意書きを置く |
| **学生にCS業務の経験がない** | ケース文にSlackの実際の文面（深夜1時の「まだ直らないんですか」など）を入れて具体で想像させる。配布データにも生の文面が大量にある |
| **B2Bのカスハラが典型イメージから外れる** | 背景で「顧客等には取引の相手方も含まれる」ことを明記する。盲点であり、同時に新鮮さの源でもある |
| 合成データが作りにくい | 骨格（場面×言動×継続時間×対応×結果）の組み合わせで生成し、口語の揺れとCS35名の書き癖を後から注入する |

## 8. お願いしたいこと

次の4点についてご意見をいただきたいです。

1. **3案のうち、どれを本番で使うか。** 1案に絞るか、2案を用意して参加者に選ばせるか
2. **Cの「課題発見型」という設計をどう見るか。** ゴールを渡さないぶん回答の広がりは最大になりますが、2日間で課題設定から始めさせる負荷があります
3. **①②③の観点で、評価が私たちの見立てと食い違う点はあるか。** 特にCを推す見立てになっていますが、反対の見方があれば聞きたいです
4. **Cのセンシティブさの扱い。** ハラスメントを題材にすることについて、参加者への配慮として足りない点はないか

### 参考：3案を並べた所感

①②③のいずれでもCが優位です。Aは因果の追いやすさで勝りますが、**業界が学生に遠いという弱点はケース文の工夫では埋めきれません**。Bは「交渉で問題を消す」という技術外の筋が出る点に独自の価値がありますが、題材としての地味さは残ります。

Cには2つの実務上のリスクがあります。1つは**作るデータが最も多い**こと（構造化約130万行、自由記述はチケット本文24万行＋Slack 3.5万件で3案中最大）。もう1つは**課題発見型であること自体**で、2日間という尺に対して課題設定から始めさせるのは負荷が高く、運営の引き上げが要ります。

なお、AとBを課題発見型にすることもできますが、Bは「同じことを4回書き直す苦痛」がデータだけからは見えにくい（時間は測れても、辛さは人の中にある）ため向きません。**課題発見型に耐えるのはCだけ**で、これはCの長所として説明できます。
